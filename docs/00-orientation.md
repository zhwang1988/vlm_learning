# 00 · 技术版图：多模态到底在解决什么问题

> 对应 Day 1

## 概念

### 问题的一句话定义

**让模型把「像素」和「文字」放进同一个语义空间里，并且能在这个空间上做推理和生成。**

听起来简单，难在两件事：

1. **表示鸿沟**：图像是稠密的、连续的、空间局部的；语言是离散的、序列的、语义全局的。两者没有天然的对应关系。
2. **数据鸿沟**：文本有互联网规模的高质量数据；图文对的质量和规模都差一大截，而且「图里的信息」远比一句 caption 丰富——一张商品图里可能有材质、版型、色差、背景、模特姿势，caption 只能覆盖很小一部分。

这两件事决定了整个领域的技术路线。

### 三条技术路线

这是理解全局最有用的一个分类。三种路线回答的是同一个问题：**图像信息以什么形式进入语言模型？**

```
路线 A · 对比学习式（Contrastive）
  ┌──────┐   ┌──────┐
  │ Image│   │ Text │
  │  Enc │   │  Enc │
  └──┬───┘   └──┬───┘
     └────┬─────┘
     投影到同一空间，算相似度
     → CLIP / SigLIP / ALIGN
  能力：检索、分类、零样本
  不能：生成、多轮对话、复杂推理

路线 B · 融合式（Fusion / Cross-Attention）
  ┌──────┐
  │Vision│──┐
  └──────┘  │  ┌──────────────┐
            ├─→│ LM + 交叉注意力 │→ 生成
  ┌──────┐  │  └──────────────┘
  │ Text │──┘
  → Flamingo / Idefics / Kosmos
  能力：交错图文、少样本
  代价：要给 LM 加新参数、训练不稳定

路线 C · 外挂式（Adapter / Projection） ← 当前主流
  ┌──────┐  ┌─────────┐  ┌──────┐
  │Vision│→ │Connector│→ │  LLM │→ 生成
  │  Enc │  │ (投影层) │  │(冻结)│
  └──────┘  └─────────┘  └──────┘
  → LLaVA / Qwen-VL / InternVL / 几乎所有现代 VLM
  能力：直接复用预训练 LLM 的语言能力和知识
  代价：视觉信息被压成有限个 token，细节会丢
```

**为什么路线 C 赢了？** 因为 LLM 已经被证明是极强的通用推理器，它的参数里装着世界知识。与其重新设计一个融合架构，不如**把图像「翻译」成 LLM 能读的 token**，让 LLM 用原有的能力去处理。工程上更简单、可复用、可扩展。

这个选择带来一个直接后果，也是本课程最核心的工程张力：

> **图像最终会被压成 N 个 token 塞进 LLM 的上下文。N 太小则细节丢失，N 太大则显存和延迟爆炸。**

你在 Day 4 会看到 Qwen2.5-VL 花了多少功夫来解决这个矛盾（原生动态分辨率），在第 2–3 周会亲身感受到它带来的数据构造和训练显存问题。

### 一张技术树

```
多模态模型
├── 理解（Vision → Language）          ← 本项目主线
│   ├── 图像分类 / 检索         (CLIP 系)
│   ├── 视觉问答 VQA            (早期：专用模型 → 现在：通用 VLM)
│   ├── 文档理解 DocVQA/OCR     (Qwen-VL、InternVL 强项)
│   ├── 视觉定位 Grounding      (输出 bbox)
│   └── 视频理解                (时序建模)
├── 生成（Language → Vision）
│   ├── 文生图                  (Diffusion / DiT)
│   └── 图生视频
└── 统一（Any-to-Any）
    ├── 交错生成                (Chameleon / Emu)
    └── 原生多模态              (GPT-4o 类)
```

本项目聚焦 **理解方向**，因为客服场景就是理解问题：用户发图 + 发文字，模型要理解并给出解决方案。生成方向（文生图）和客服无关，不碰。

### 代表模型速查

| 模型 | 视觉编码器 | 连接器 | 主干 | 特点 |
|---|---|---|---|---|
| LLaVA-1.5 | CLIP ViT-L/336 | 2 层 MLP | Vicuna | 极简，学术基线 |
| LLaVA-NeXT | CLIP + AnyRes | MLP | Vicuna/Mistral | 多分辨率切图 |
| BLIP-2 | EVA-CLIP | Q-Former | OPT/FlanT5 | 连接器设计的经典 |
| InternVL 2.5/3 | InternViT-6B | MLP (pixel shuffle) | InternLM/Qwen | 视觉塔大，细粒度强 |
| Qwen2-VL | ViT + Naive DynRes | MLP | Qwen2 | M-RoPE |
| **Qwen2.5-VL** | ViT + Window Attn | MLP | Qwen2.5 | **本项目基座** |
| GPT-4o / Gemini | 未公开 | 未公开 | 未公开 | 原生多模态 |

### 为什么选 Qwen2.5-VL 作基座

1. **中文场景最强**：中文 OCR、中文文档、中文商品图理解明显优于 LLaVA/InternVL 的英文中心模型。客服场景全是中文。
2. **动态分辨率是刚需**：商品图有长图（详情页）、横图（banner）、方图。固定分辨率会严重变形。Qwen2.5-VL 原生支持任意比例。
3. **链接器最简、最容易改**：MLP 连接器意味着你可以很方便地替换视觉塔或者插 LoRA。
4. **工具链完备**：transformers / vLLM / LLaMA-Factory / ms-swift 全都第一时间支持，无卡环境下最容易跑起来。
5. **3B 版本能在 Colab 上训**：这是没有本地算力时唯一现实的选择。


## 工程细节

### 一个必须先建立的直觉：视觉 token 的代价

假设一张 1024×1024 的图，ViT patch size = 14：

```
patch 数 = (1024/14) × (1024/14) ≈ 73 × 73 ≈ 5329 个 patch
```

如果每个 patch 变成 1 个 token，那就是 **5329 个 token**。对比一下：一段 500 字的中文回答大约 700 个 token。

也就是说，**一张图的开销相当于 7 段长回答**。这就是为什么：

- 所有 VLM 都要做 token 压缩（Qwen2.5-VL 做了 2×2 的 patch merging，5329 → 约 1332）
- 训练时 batch size 开不大
- 多图场景极其昂贵
- 长上下文 + 高分辨率 = 显存杀手

**记住这个数字关系，后面每一周的显存问题都能从它推导出来。**

### 现代 VLM 的标准前向流程

```python
# 伪代码，每一步在 src/minivlm/ 里都有真实实现
images → VisionEncoder → (B, num_patches, D_vision)      # 视觉特征
                        ↓
        Connector (MLP/Resampler) → (B, N_vis, D_llm)    # 投影到 LLM 维度
                        ↓
text → Tokenizer → ids → Embedding → (B, N_txt, D_llm)   # 文本嵌入
                        ↓
   把 <image> 占位符替换为 N_vis 个视觉嵌入，拼接
   [txt_1..txt_k, VIS_1..VIS_N, txt_{k+1}..]
                        ↓
              LLM (Qwen2.5) → logits → 生成
```

**关键点**：图像不是「加」进模型的，是「插」进 token 序列的。所以图像在序列中的位置（前面/中间/后面）会影响模型理解，也影响 attention mask 的构造。
