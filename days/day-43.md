## 二、写（100 min）

`scripts/loadtest.py`（今日新增，已给实现）

| 函数 / 文件 | 你要做什么 |
|---|---|
| `worker()` | 异步并发发请求，记录每次的延迟与状态码 |
| `--concurrency` | 并发度；从 1 开始翻倍，找到拐点 |
| P50 / P95 / P99 | 分位数统计 —— 平均值没有意义 |
| `--duration` | 按时长而不是按请求数压（更接近真实流量） |
| 成本核算 | 把压测吞吐换算成「单卡能吃多少店」，再对照定价算毛利 |

## 三、跑（在云 GPU 上）

```bash
# 压 200 个请求，并发 10
python scripts/loadtest.py --url https://your-app.onrender.com/v1/chat --n 200 --concurrency 10
# 并发 1 的基线（用来算加速比）
python scripts/loadtest.py --url ... --n 200 --concurrency 1
# 再压一次，看拐点在哪
python scripts/loadtest.py --url ... --n 200 --concurrency 20
```

期望输出（节选）：

## 五、容易踩的坑

1. **只测吞吐不测 P95** —— 平均值 1.7 秒听起来很好，但 P95 是 3.9 秒，那 5% 的用户体验到的就是「这破玩意儿太慢」。
2. **漏算闲置 GPU 时长** —— 你不可能 24 小时满载，按满载算成本会严重低估。
3. **漏算 Shopify 抽成** —— 平台分成是实打实的成本项。
4. 压测用的是自己的开发数据 —— 真实用户的图更大、问题更复杂，延迟会更高。要留 2–3 倍余量。
5. 只测文本不测图文 —— 带图的请求延迟是纯文本的 2–3 倍，必须分开压。
6. 压测打到生产库 —— 压测数据污染真实数据。用独立的测试店铺。
